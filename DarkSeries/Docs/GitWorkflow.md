# DarkSeries Git 작업 규칙

## 1. 문서 목적

기능별 작업을 이슈 단위로 추적하고, 독립된 브랜치에서 구현한 뒤 검토를 거쳐 병합하기 위한 기본 규칙이다.

이 문서는 초기안이다. 실제 작업 방식이 정해지면 브랜치 종류, 커밋 언어, 병합 방식 등을 구체화한다.

## 2. 기본 작업 흐름

```text
이슈 생성
  → 최신 Dev에서 이슈 브랜치 생성
  → 구현 및 검증
  → 의미 있는 단위로 커밋
  → Dev 대상 Pull Request 생성
  → 검토 및 수정
  → Dev 브랜치에 병합
  → 이슈 종료
```

원칙적으로 하나의 브랜치는 하나의 이슈만 처리한다. 작업 중 별도의 문제가 발견되면 현재 이슈의 범위를 불필요하게 넓히지 않고 새 이슈로 분리한다.

`main`은 배포 또는 안정 버전을 위한 브랜치로 사용한다. `Dev`에서 `main`으로의 병합은 일반적인 이슈 작업 흐름에 포함하지 않는다.

## 3. 이슈 작성 기본 틀

### 이슈 제목

```text
[유형] 구현하거나 해결할 내용
```

예시:

```text
[Feature] SwordMaster 달리기 상태 구현
[Bug] 공중에서 걷기 상태로 전환되는 문제 수정
[Docs] 플레이어 상태 구조 문서화
```

### 이슈 본문

```md
## 목적

이 작업이 필요한 이유를 작성한다.

## 작업 범위

- 구현하거나 수정할 내용
- 영향을 받는 시스템 또는 파일

## 완료 조건

- [ ] 기능 구현
- [ ] 관련 동작 검증
- [ ] 문서 갱신 여부 확인

## 제외 범위

- 이번 이슈에서 다루지 않을 내용

## 참고 사항

- 관련 문서, 이미지, 이전 이슈 또는 주의 사항
```

### 권장 이슈 유형

| 유형 | 용도 |
|---|---|
| `Feature` | 새로운 기능 추가 |
| `Bug` | 잘못된 동작 수정 |
| `Refactor` | 기능 변화 없는 구조 개선 |
| `Docs` | 문서 추가 및 수정 |
| `Test` | 테스트 추가 및 검증 개선 |
| `Chore` | 설정, 에셋 정리, 개발 환경 작업 |

## 4. 브랜치 규칙

### 기본 형식

```text
issue/<이슈번호>-<짧은-설명>
```

예시:

```text
issue/12-swordmaster-run
issue/18-fix-air-transition
issue/24-update-state-docs
```

### 작성 규칙

- 영문 소문자와 숫자를 사용한다.
- 단어는 하이픈(`-`)으로 구분한다.
- 브랜치 이름은 짧고 작업 목적을 알아볼 수 있게 작성한다.
- 하나의 브랜치에 서로 관련 없는 이슈를 함께 처리하지 않는다.
- 모든 이슈 브랜치는 최신 `Dev` 브랜치에서 생성한다.
- 이슈 브랜치를 `main`에서 직접 생성하거나 `main`에 직접 병합하지 않는다.

## 5. 커밋 메시지 규칙

### 기본 형식

```text
<type>: <변경 내용> (#이슈번호)
```

예시:

```text
feat: 달리기 상태와 입력 전환 추가 (#12)
fix: 공중 상태 전환 중 걷기 진입 방지 (#18)
docs: 상태 머신 구조 문서 갱신 (#24)
```

### 커밋 타입

| 타입 | 용도 |
|---|---|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변화 없는 코드 구조 변경 |
| `docs` | 문서 변경 |
| `test` | 테스트 변경 |
| `chore` | 설정, 에셋, 도구 등 기타 작업 |
| `style` | 동작과 무관한 형식 변경 |
| `perf` | 성능 개선 |

### 메시지 작성 원칙

- 제목만 읽어도 무엇을 변경했는지 알 수 있게 작성한다.
- 구현 방법보다 변경 결과를 중심으로 작성한다.
- 한 커밋에는 하나의 논리적인 변경만 포함한다.
- 관련 없는 파일이나 사용자 작업을 함께 커밋하지 않는다.
- 임시 메시지인 `수정`, `작업`, `테스트`만 단독으로 사용하지 않는다.
- 추가 설명이 필요하면 제목 아래에 빈 줄을 두고 본문을 작성한다.

### 커밋 본문 선택 형식

```text
feat: 달리기 상태와 입력 전환 추가 (#12)

- Run 입력 시작과 취소 처리
- Idle과 Walk 상태에서 Run 전환 연결
- Animator Run 파라미터 연동
```

## 6. 커밋 전 확인

- 현재 브랜치가 해당 이슈 브랜치인지 확인한다.
- Git diff를 검토해 의도하지 않은 변경이 없는지 확인한다.
- 씬, Animator, Animation Clip, Input Actions, `.meta` 변경이 필요한 변경인지 확인한다.
- 가능한 컴파일, 테스트 또는 정적 검사를 수행한다.
- Unity Editor 검증이 필요하지만 수행하지 못했다면 Pull Request에 기록한다.
- 관련 문서의 갱신이 필요한지 확인한다.

## 7. Pull Request 기본 틀

모든 이슈 Pull Request의 대상 브랜치는 `Dev`로 지정한다.

### 제목

커밋 제목과 같은 형태를 기본으로 사용한다.

```text
feat: 달리기 상태와 입력 전환 추가
```

### 본문

```md
## 관련 이슈

- Closes #12

## 변경 내용

- 주요 변경사항
- 영향받는 시스템

## 검증

- [ ] 코드 컴파일
- [ ] Unity Play Mode 확인
- [ ] 관련 상태 전환 확인

## 확인이 필요한 부분

- 리뷰 시 집중해서 볼 내용
- 수행하지 못한 검증

## 변경된 Unity 에셋

- 씬, Prefab, Animator, Animation Clip, Input Actions, `.meta` 변경 여부
```

## 8. 병합 규칙

- Pull Request 검토와 필요한 검증이 끝난 뒤 병합한다.
- 충돌은 변경 의도를 확인한 뒤 이슈 브랜치에서 해결한다.
- 병합 전에 관련 없는 변경이 포함되지 않았는지 다시 확인한다.
- 모든 이슈 브랜치는 `Dev` 브랜치로 병합한다.
- 이슈 브랜치를 `main` 브랜치에 직접 병합하지 않는다.
- `Dev` 브랜치를 `main` 브랜치에 병합하는 작업은 사용자의 명시적인 요청이 있을 때만 진행한다.
- 사용자가 `Dev`에서 `main`으로의 병합을 요청했더라도 즉시 병합하지 않는다. 대상 브랜치, 포함되는 변경사항, 검증 결과를 제시하고 병합 직전에 사용자에게 다시 확인받는다.
- 재확인에 대한 명시적인 승인을 받은 뒤에만 `Dev`를 `main`에 병합한다.
- 병합 방식은 프로젝트에서 최종 결정한 방식을 따른다.

### 추후 결정할 항목

- [ ] Merge commit, Squash merge, Rebase merge 중 사용할 방식
- [ ] 커밋 메시지의 한국어 또는 영어 사용 기준
- [ ] Pull Request 승인 필요 여부
- [ ] 브랜치 삭제 시점
- [ ] 버전 태그와 릴리스 방식

## 9. Codex 작업 시 적용

- Codex는 이슈 번호와 작업 범위를 확인한 뒤 해당 범위만 작업한다.
- 사용자의 명시적인 요청 없이 이슈 생성, 브랜치 생성, 커밋, 푸시, Pull Request 생성, 병합을 수행하지 않는다.
- 이슈 Pull Request는 `Dev`를 대상으로 생성한다.
- `Dev`에서 `main`으로 병합하라는 요청을 받으면 변경 범위와 검증 상태를 먼저 보고하고 별도의 최종 승인을 요청한다.
- 기존 작업 트리의 변경사항과 Codex가 만든 변경사항을 구분한다.
- 커밋 요청을 받으면 포함할 파일과 diff를 먼저 확인한다.
- 작업 결과에는 변경 내용과 수행한 검증, 남은 검증 사항을 기록한다.
